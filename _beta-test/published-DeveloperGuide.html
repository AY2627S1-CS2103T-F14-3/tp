Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app’s work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete-client 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component’s implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.

Model component

API : Model.java

The bakeryitem package forms the bakery-item subcomponent of the Model component:

The order package forms the client orders subcomponent of the Model component.

The Model component,

  • stores client (represented by Person), bakery-item, and order data in unique collections.
  • stores the Person, BakeryItem, and ClientOrder objects selected by their current filters in separate filtered lists. It exposes these lists as unmodifiable observable lists that the UI can observe and bind to, so the UI updates when any of these lists changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)
Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both bakery book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component’s job is to save/retrieve objects that belong to the Model)

Implementation

Clear confirmation

The following class diagram shows how clear-command parsing stores the confirmation choice in a ClearCommand.

ClearCommandParser accepts only no arguments or the exact token confirm. An unconfirmed ClearCommand throws a CommandException containing the warning before modifying the model. This also prevents the normal save path from running. A confirmed command clears the complete bakery book and resets client/item filters; the existing logic-layer save rollback restores data and filters if persistence fails.

The confirmation is explicit in clear confirm, with no pending state or dialog. It is a one-shot command for experienced users and executes even without an earlier clear; there is no additional confirmation. Users cancel an unconfirmed request by continuing with another command. Both the warning and Help usage explicitly state that clear confirm deletes all clients, items, and orders immediately.

The warning formats counts from the complete ReadOnlyAddressBook lists, rather than the filtered UI lists, so it includes hidden records. Counts are calculated when clear runs and are not a stored preview; clear confirm always acts on the book at execution time. Help reuses ClearCommand.MESSAGE_USAGE. ClearConfirmationTest exercises parsed commands, persistence, hidden records and counts, repeated warnings, invalid confirmations, and save-failure rollback.

Integration with single-step undo (issue #97)

Clear confirmation and single-step undo share the normal LogicManager persistence path. Confirmation protects against accidental deletion; undo provides one opportunity to restore a successfully cleared book.

  • An unconfirmed request throws before changing the model and before saving. Invalid syntax fails in the parser. Neither reaches the undo snapshot update.
  • After a confirmed clear saves successfully, the undo logic compares before/after data. If the book changed, its existing complete pre-command snapshot becomes the one undo opportunity. An already empty book produces no data change and leaves the previous snapshot intact.
  • If saving the clear fails, normal rollback restores all records and both filters. The undo snapshot must remain unchanged because it is updated only after a successful save.
  • Undo restores the complete pre-clear book, including order UUIDs, item/client associations, quantities, deadlines, statuses, and insertion order. It resets displayed filters and consumes its snapshot only after the restored data saves successfully.
  • If saving undo fails, retain the snapshot and restore the empty pre-undo book and its filters so retry remains possible. Later successful data changes replace the snapshot. Restarting discards it; redo is unsupported.

No confirmation flag needs to be stored in the model, data file, or undo snapshot. Use the parsed confirmation flag only for that command execution.

Command history

CommandHistory holds submitted text, a navigation cursor, and the unsent draft for one application session. CommandBox records non-empty submissions before execution, including commands that produce handled errors, and resets navigation after each submission.

An event filter consumes unmodified Up/Down key presses. Up saves the draft when navigation starts and recalls older commands; Down recalls newer commands and eventually restores the draft. Recalled text is copied into the input with the caret at its end, so editing it does not modify a stored entry. Other keys and modified arrow shortcuts retain their existing behavior. History does not change the model or storage.

CommandHistoryTest covers boundaries, draft restoration, repeat submissions, and editing. CommandBoxTest dispatches JavaFX key/action events to verify integration and recovery of failed commands.

This section describes some noteworthy details on how certain features are implemented.

Single-step undo

LogicManager keeps one in-memory AddressBook snapshot. After a command saves successfully, it compares the before/after data and replaces the snapshot only if data changed. Read-only commands, no-op edits, and failed commands leave it intact.

The parser recognizes undo without arguments. Logic supplies the snapshot to UndoCommand, which restores all clients, items, and orders and resets the displayed client/item filters. The normal persistence path saves the result. Only a successful save consumes the snapshot; on save failure, the existing rollback restores pre-undo data and filters, retaining the snapshot for retry.

Users invoke undo by typing undo in the command input. When no snapshot is available, the command reports an error without changing data. Snapshots preserve immutable records, their associations, order UUIDs, and insertion order. No redo or persistent history is provided.

A complete snapshot keeps recovery consistent across linked entities without implementing a separate inverse for each command. It uses memory proportional to one bakery book. UndoTest covers persistence, linked records, duplicate orders, snapshot replacement, no-op/failed commands, and save failure. UndoCommandUiTest verifies command-box submission, persisted recovery, and feedback when undo succeeds or is unavailable.

Client order backend

add-order CONTACT_INDEX i/ITEM_INDEX q/QUANTITY d/DEADLINE resolves indices from the displayed client and bakery item lists and adds an incomplete order. Identical orders are accepted with separate UUIDs. Quantities remain integers from 1 to 9,999; deadlines use strict YYYY-MM-DD calendar dates, including past dates. Missing, repeated, malformed, overflowing, and out-of-range arguments cannot change data.

AddressBook owns observable client, bakery item, and order collections. Orders reference immutable clients and items rather than displayed positions. Editing a client or bakery item updates its order references while retaining order IDs and the other order details. Deleting a referenced client or item is blocked until its orders are removed. Clearing the book clears all three collections together. The model exposes displayed item lists and client-local order lists; the logic exposes unmodifiable observable item and order lists for the teammate’s list and GUI implementation.

The JSON file contains persons, bakeryItems, and orders. Legacy AB3 files without items or orders remain supported. Each order stores an id UUID, clientName, itemName, quantity, deadline, and complete status. Client and item names reference their respective unique collection entries, preserving associations if the collections are reordered. In-app client and bakery item edits update both the edited record and its order references. Manual renames in JSON must update the corresponding order references too. Duplicate order UUIDs, missing references, invalid values, and null entries are rejected during loading; no partially loaded model is returned.

Commands return success only after persistence succeeds. The storage writes a temporary JSON file beside the destination and replaces the destination, using an atomic move where supported. A failed save restores the previous model, displayed filters, and order comparator. The shared order APIs support deletion, completion changes, and replacement of order details in place.

add-item from team PR #34 is integrated with the shared item model and storage so orders can reference real bakery goods. Order views and list commands remain the assigned teammate’s GUI work.

Client order editing

edit-order CONTACT_INDEX o/ORDER_INDEX [i/ITEM_INDEX] [q/QUANTITY] [d/DEADLINE] is dispatched to EditClientOrderCommandParser. The parser normalizes whitespace and requires a client index, exactly one order prefix, and at least one editable field. It rejects repeated prefixes and validates indices, quantity, and strict calendar dates using the existing parsers, including valid past deadlines.

EditClientOrderCommand resolves the displayed client and its full client-local order list through OrderCommandUtil#findOrder(). An optional item index resolves against the displayed bakery item list. It constructs an immutable replacement, retaining omitted values, UUID, client, and completion status. Only after all validation succeeds does ModelManager#setOrder() delegate to AddressBook#setOrder(). The latter validates the existing target and the replacement’s retained fields and item reference, then replaces the selected element at its original position. Repeat orders retain separate identities.

Observable filtered/sorted views update from the replacement without resetting predicates or comparators. An edit can change search membership or deadline ordering while retaining the client-local order number. LogicManager saves the complete book before returning success. I/O or permission failures restore the snapshot, all three filters, and the order comparator, retaining any prior undo opportunity. A saved change becomes the single-step undo snapshot; an equal-value edit skips replacement and does not replace undo history. Undo restores the prior book and shows all lists, following existing behavior. No storage schema change is needed.

Bakery item editing

edit-item INDEX [n/ITEM_NAME] [p/PRICE] edits an item selected from the displayed bakery item list. The AddressBookParser delegates to EditBakeryItemCommandParser, which parses the index and the optional name and price into an EditBakeryItemDescriptor. It rejects malformed or non-positive indices, repeated prefixes, invalid field values, and requests that provide neither editable field.

During execution, EditBakeryItemCommand resolves INDEX against Model#getFilteredBakeryItemList() and creates an immutable replacement item. An index outside the displayed list is rejected without mutation, and omitted fields retain their existing values. Before mutation, the command rejects a new name that matches another item’s name after case and whitespace normalization.

For a successful edit, ModelManager#setBakeryItem() delegates to AddressBook#setBakeryItem(). The unique bakery item list replaces the original item, and each order that references it is replaced using ClientOrder#withItem(). This retains the order’s UUID, client, quantity, deadline, and completion status while associating it with the edited item. The command then displays the complete bakery item list. Persistence and rollback on a save failure follow the same Logic transaction used by other data-changing commands.

Deleting a client order

AddressBookParser dispatches delete-order CONTACT_INDEX o/ORDER_INDEX to DeleteClientOrderCommandParser, which requires a positive client index and exactly one positive o/ order index. Missing, repeated, empty, malformed, overflowing, or extra arguments are rejected.

DeleteClientOrderCommand uses OrderCommandUtil#findOrder() to resolve the client from the displayed client list and the order from that client’s full order list, including orders hidden by an order filter. Out-of-range indices report an error before any data changes. These positions are not persistent identifiers.

The command passes the selected ClientOrder to Model#deleteOrder(). Only that order is removed; identical repeat orders retain their separate identities. Observable order views update automatically, and later order numbers within the same client shift down after deletion.

LogicManager saves the updated book before returning the Order deleted: success message. A save failure restores the previous data, displayed filters, and order comparator. A successful deletion becomes the single-step undo opportunity, allowing undo to restore the deleted order and its associations.

Order completion alias

AddressBookParser dispatches both mark CONTACT_INDEX o/ORDER_INDEX and mark-order-complete CONTACT_INDEX o/ORDER_INDEX to MarkOrderCompleteCommandParser. Both produce the same MarkOrderCompleteCommand, so validation, client-local order selection, already-complete errors, persistence, save-failure rollback, and single-step undo remain shared. The command usage and help window list both spellings.

Manual check: launch the JAR in a disposable writable folder, never a folder containing real bakery data. Run clear confirm to remove the initial sample data, then create one client, one item, and two identical orders for client 1. Run mark 1 o/2 and verify that only the second order becomes complete. Restart to verify persistence, then run unmark 1 o/2, mark 1 o/2, and undo to verify the second order returns to incomplete. Try both command spellings with missing indices, o/0, and repeated o/ prefixes; verify identical errors and no data changes.

Appendix: Requirements

Product scope

Target user profile:

  • runs a home bakery business
  • has a need to manage a significant number of client contacts
  • has a need to manage a significant number of client order details
  • prefers desktop apps over other types of applications
  • can type fast
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: Help home bakers running a home bakery business manage client contacts and orders faster than with a typical mouse-driven GUI application.

Non-Functional Requirements

  1. The application should run on any mainstream operating system with Java 25 installed.

  2. With up to 100 client contacts, 100 bakery goods and 1000 orders, the application should display the results of a list, search or filter command within 3 seconds on the project team’s reference machine running Java 25.

  3. After a data-changing command reports success, the affected client, bakery good or order data should be retained after the application is closed and reopened, with its values and associations unchanged.

  4. A first-time user with basic computer literacy should be able to use the in-app help to add a client, bakery good and order within 15 minutes, without outside assistance.

  5. Client contact, bakery good and order data should remain on the user’s computer. The application should not transmit this data over a network.

Glossary

  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Private contact detail: A contact detail that is not meant to be shared with others
  • Baker: The user who manages clients, bakery goods and orders in BakeBase.
  • Client: A customer whose contact details are stored in BakeBase.
  • Bakery book: The collection of client, bakery item, and order data inside BakeBase. This is represented by AddressBook in the code and was adapted from the address book in AB3.
  • Bakery good: A baked product that a baker offers and can add to a client order.
  • Bakery item: Another term for a bakery good. The terms are used interchangeably in this guide.
  • Client order: A record of a client’s request for a bakery good, including its quantity and, if specified, its deadline and status.
  • Order deadline: The date by which a client order is due.
  • Incomplete order: An order that has not been marked as complete.
  • Completed order: An order that the baker has marked as complete.
  • Recurring order: An order pattern saved for reuse when a client regularly requests the same order.
  • Membership tier: A client category that determines the membership options or discounts available to that client.
  • Limited-edition bakery good: A bakery good offered for a limited period.
  • Special instructions: Notes associated with an order, such as allergy information or preparation requests.
  • Ingredient inventory: The recorded quantities of ingredients available for fulfilling orders.
